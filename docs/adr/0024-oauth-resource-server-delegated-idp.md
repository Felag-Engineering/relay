# Relay is an OAuth 2.1 protected resource, never an authorization server

**Status:** Accepted.

MCP's authorization layer lets a human connecting their own harness (Claude, or any
off-the-shelf MCP client) obtain a token through a flow they complete themselves, so the
session runs under **their** identity rather than a shared machine credential. #299 adopts
that layer. This ADR records the decision the issue asked to be settled inside it: whether
the Relay issues those tokens itself or validates tokens issued elsewhere.

## Decision

**The Relay is a protected resource only.** It validates OAuth tokens issued by a
configured external identity provider and resolves them to Accounts. It has no
authorization endpoint, no token endpoint, no client registration, and no consent screen —
and gains none of them later without a separate ADR.

Concretely:

- The MCP endpoint publishes **RFC 9728 protected-resource metadata** at
  `/.well-known/oauth-protected-resource`, naming the configured issuer as its
  authorization server, and its 401s carry `WWW-Authenticate: Bearer resource_metadata=…`
  so a standard harness can discover the flow without any Relay-specific configuration.
- Tokens are verified against the IdP's JWKS (signature, issuer, audience, expiry).
- The token's configured claim maps to an **existing** Account by name. There is **no
  auto-provisioning**: an unrecognized subject is refused.
- Static per-Account API Tokens (#296) remain, unchanged, for headless drivers. The two
  credential kinds are routed by prefix, never tried in turn — the rule ADR-0023 already
  established.

## Why not be our own authorization server

This is not a close call, for a reason specific to where Relay is today.

**An authorization-code flow needs a browser-facing login and consent surface, and Relay
has neither.** There is no web UI at all — the Admin Console is v0.6.0/v0.7.0 — and no
human credential: `accounts.Account` has no password field and no column for one. Becoming
an authorization server would mean building, in this milestone, a login page, a session
mechanism, a consent screen, token issuance, and refresh handling — a large new attack
surface, on the same listener that executes commands on the fleet, defended by
hand-rolled code with no operational history.

Three further reasons, each sufficient on its own:

- **Every organization that would run Relay already has an IdP.** Federating is what they
  expect. A second identity silo with its own passwords is what they actively don't want,
  and it would put Relay in the business of password resets and MFA.
- **It keeps the human-credential question where ADR-0010 already put it** — the Console
  milestone — rather than pre-deciding it here, in a hurry, under a different issue.
- **It is reversible in the right direction.** Adding authorization-server endpoints later
  is additive. Having built one and migrating customers off it is not.

**Recorded direction:** if Relay ever becomes its own authorization server, it should be
after the Console's login surface exists and should reuse it, not stand up a parallel one.

## Why go-oidc rather than hand-rolled verification

Token verification is added as a dependency (`github.com/coreos/go-oidc/v3`), not written
here. JWT validation is a well-known source of catastrophic, quiet bugs — `alg: none`,
algorithm confusion, unverified `kid` selection, key-rotation races — and every one of them
fails open. The library does OIDC discovery, JWKS caching and rotation, and algorithm
pinning; the MCP Go SDK supplies the RFC 9728 metadata handler and the `WWW-Authenticate`
middleware shape. The code that belongs to us is the part that is genuinely ours: mapping a
verified claim to an Account, and refusing when it does not map.

## What this does NOT change

**An OAuth session does not make a call human-grade.** The design note
(`docs/design/approval-and-attribution.md`) is explicit and this ADR restates it because it
is the thing most likely to be misread:

> An OAuth session through MCP proves a human authorized the **session** — not that a human
> intended each **call**. The tool calls are still generated by a model, and the session can
> be steered by prompt injection in content the model read.

So **MCP-originated calls remain agent-grade for approval gating regardless of whose
identity authorizes the session** (#274, #283, and v0.5.0's gating). What an OAuth session
buys is attribution and revocation, not trust. The discriminating axis for gating is how
strongly a surface binds a human's intent to an individual action, and MCP binds it
weakly by construction.

Nothing in this ADR changes the role ladder either: an OAuth session's authority is the
role of the Account it resolves to. A human authenticating through an IdP gets `operator`
if their Account is an operator, and Raw Exec still requires `admin`.

## Consequences

- **Relay gains a runtime dependency on the IdP's availability** for OAuth sessions.
  Deliberately bounded: API Tokens are verified entirely locally, so a fleet driven by
  machine Accounts is unaffected by an IdP outage. The bootstrap credential is likewise
  local, so an operator is never locked out of their control plane by someone else's
  downtime.
- **Account provisioning stays a deliberate admin act.** Auto-creating an Account from a
  token claim would let whoever administers the IdP mint identities on the control plane,
  and would bypass the audited creation path (#297). The cost is a manual step when
  onboarding a human: create the Account, then they can authenticate.
- **Group/team federation is not built here.** `on_behalf_of` remains the free-form
  asserted field (#300). Federating IdP groups is the named later direction, and it wants
  the Console's OIDC work to land first so both surfaces read groups the same way.
- **OAuth configuration is Relay configuration** — a root-owned local file and flags, never
  reachable through the Control API (invariant 11). An API that could repoint its own
  issuer could authenticate anyone.
