# v0.2.2 — Execution: the Control API hands back the Job; call-shape checks move into the layer

**Spec:** `docs/specs/execution.md` — claims EX-57, EX-58, EX-59, EX-60, EX-64, EX-66, EX-67; re-proves PF-13 (`docs/specs/policy-preflight.md`)
**Milestone:** v0.2.2   **Opened:** 2026-11-16

## Intent

The Control API stops blocking until the whole Job is done. It hands back the Job the way MCP does, and in the same change it accepts `Idempotency-Key`, so a caller who loses the response can always retry safely (EX-57, EX-58). Three checks that the adapters make today, unaudited, move into the capability layer at the stage of EX-61: Native argument names (EX-64), an empty Raw Exec argv (EX-67) and a Task timeout above 300 seconds (EX-59). If the outcome write fails after the Job ID has gone back, the failure is recorded on the Job (EX-66). `list_operations` says that arguments are audited verbatim (EX-60).

## Shape

**Seams that stay fixed:**
- `capability.Execution.Start`, `StartOptions` and `StartedJob`: no signature change.
- `prepareDispatch`'s stage order (EX-3).
- `resolveAction` stays "computes, never refuses": a refusal goes back as data and is acted on after authorization.
- `jobs.Action`, `/proto`, and the daemon's 30 s default and 300 s cap (EX-24).
- `Execution.Run` stays for `cmd/relay/devharness.go` and the capability tests. After S2 no adapter calls it.

**S1, the shared wait** (`relay/internal/controlplane/execution.go`, `mcp/tools_execution.go`):
- Add `controlplane.AwaitStartedJob(ctx, sj capability.StartedJob, wait time.Duration)`. It returns when `sj.Done` closes, when the wait lapses or when ctx ends. It returns at once when `wait` is 0 or `sj.Reattached` is set.
- MCP's `dispatch` calls it in place of its own select. MCP behaviour does not change.

**S2, EX-57 and EX-58 (#1317)** (`api/execution.go`, `api/jobs.go`, OpenAPI, scripts, `cmd/relay` tests):
- `api.Executor` swaps `Run` for `Start`, matching `mcp.Executor.Start`. The api test `fakeExecutor` follows.
- Both dispatch bodies gain `wait_seconds`, checked by `controlplane.ResolveWaitSeconds` (0 to 300, default 0, a 400 outside that range). It is presentation only and never reaches the layer.
- `dispatchOrPlan`:
  1. reads `Idempotency-Key` into `StartOptions.IdempotencyKey`. The header is ignored when `plan: true`. More than one header value is a 400, the same transport-decode class as a bad JSON body.
  2. calls `Start`, then `AwaitStartedJob`, then `renderJob`.
  3. if the read-back fails after `Start` succeeded, returns a 500 whose detail names the Job ID, because the Job exists.
- `executionResponse` gains `job_status` (from `controlplane.RenderJob`) and `reattached` (omitempty). The status is 200 whether the Job is running or complete. 202 stays exclusively `pending_approval`.
- `jobResponse` gains `job_status`, so a poller knows when to stop.
- `writeExecError` maps the idempotency errors. The detail is the error's own text, which says whether a new key is safe.

| Error | Status |
|---|---|
| `IdempotencyConflictError` (EX-53) | 422 |
| `IdempotencyKeyError` | 400 |
| `IdempotencyPendingError`, `IdempotencyReleasedError`, `IdempotencyAbandonedError` | 409, told apart by problem title |
| `ErrIdempotencyUnavailable` | 503 |

- Callers updated in the same change:
  - `docs/api/openapi.yaml`: the header, `wait_seconds`, `job_status`, `reattached` and the statuses above.
  - `docs/STATUS.md`, Execution row.
  - Threat model R57: "(EX-35)" becomes "(EX-35, EX-57)".
  - `scripts/install-matrix-row.sh` (`facts_dispatch_succeeds`) and `scripts/install-matrix-vm-trace.sh` (`dispatch`, `wait_facts`). Each gets one helper that posts with `wait_seconds` and then polls `GET /api/v1/jobs/{id}` until `job_status` is `complete`, with a bounded number of tries. A dispatch with no wait, or a wait that lapses, comes back `running`, so polling is what makes the trace correct.
  - The `cmd/relay` tests that assume the Job, or its `KindDispatch` record, is complete when the dispatch returns: `control_api_e2e_test.go` (`JobRoutes`, `JobResultsMatchMCP`, `RefusalRendersIdenticallyOnBothSurfaces`, `HaltRendersIdenticallyOnBothSurfaces`), `approval_e2e_test.go`, `approval_release_once_e2e_test.go` (its `KindDispatch` count is now written in the background, so it waits or polls), `approval_console_absent_e2e_test.go` (`assertRestartRuns` reads `results[0].outcome` off a re-drive) and `refusal_legibility_e2e_test.go`. `newserver_test.go` uses `plan: true` only and is unaffected.

**S3, EX-64 and EX-67 (#1346)** (`capability/template.go` plus a new `capability/callshape.go`, both adapters, `approval/plan.go` (comment only), `.golangci.yml`):
- `resolvedAction` gains `callRefusal` and `callRefusalKind`. These hold refusals that need no Node.
- `resolveAction` runs `checkCallShape(act)` for every kind before Template resolution:
  - when `act.Kind == ActionOperation` and `opvocab.Lookup` finds a Native, it runs `opvocab.ValidateArgNames`. This covers unknown and missing names.
  - when `act.Kind == ActionRawExec`, an argv that is nil or empty is refused.
  - both refusals are a `MalformedCallError` with `RefusalMalformed`, which both renderers already handle.
- In `prepareDispatch`, `callRefusal` is acted on at the EX-61 stage, after the zero-match refusal (EX-3) and before `ra.refusal`.
- `Execution.Plan` acts on `callRefusal` after authorization and **whatever matched**, before any Node is queried (PF-13). The existing `!noMatch && ra.refusal != nil` guard stays only for Node-dependent Template refusals.
- Both adapters stop deciding:
  - `buildOperationAction` drops `ValidateArgNames`, and both raw-exec handlers drop the empty-argv check.
  - A forbidigo "adapter boundary" pattern forbids `opvocab.ValidateArgNames` in the three adapter packages.
- The MCP schema stops refusing what the layer now decides. Today the go-sdk refuses these before the handler runs, unaudited:
  - `argv` leaves `required` and becomes nullable again. Its description still says it must be non-empty.
  - `idempotency_key` drops `MaxLength`. Its description still says 128.
- The `HashPlan` comment names the single layer call site. The guarantee still holds, because the EX-61 stage precedes the approval gate.
- Docs:
  - Delete the invariant-10 row from the `AGENTS.md` gap table, once both checks have landed.
  - In the PF-13 row of `policy-preflight.md`, replace the name-half citation with the new capability Plan test. That file is on `docs/agents/docs-ratchet.txt` (shape, history), and migrating it is human work: S3 changes only the one proof citation, takes the exception #1275 took, and says so in its PR body.

**S4, EX-59** (`capability/callshape.go`, `controlplane/execution.go`, both adapters, OpenAPI):
- `capability.MaxTaskTimeoutSeconds = 300` and an exported `TimeoutError{Asked}` with kind `RefusalMalformed`. Its text names the ceiling and says nothing was dispatched.
- It is the last check in `checkCallShape`, for every kind. It refuses anything below 0 or above 300.
- Delete `controlplane.MaxTimeoutSeconds` (86400), `ResolveTimeoutSeconds`, and their adapter calls and tests.
- Rendering: the Control API maps it to 400 "invalid timeout_seconds", and MCP's `renderRunError` returns it verbatim.
- MCP schema: `timeout_seconds` drops `minimum` and `maximum`, leaving the reflected int32 range. The description says "0 = daemon default of 30; max 300, refused above".
- OpenAPI sets `maximum: 300`. The server does not enforce the document.

**S5, EX-66** (`jobs`, `store`, `capability/pipeline.go`, `controlplane/render.go`, both adapters' Job outputs, OpenAPI):
- `jobs.Job` gains `OutcomeAuditFailedAt time.Time`, where zero means none.
- `JobRepository` gains `RecordOutcomeAuditFailure(ctx, jobID, at)`, a first write that wins.
- A migration adds a nullable `outcome_audit_failed_at` to `jobs`, with no backfill, like `0032_job_halt.sql`.
- `account` records the failure when the `KindDispatch` or `KindJobHalt` record fails and the Job exists:
  - it writes through the Job engine, reached by a type assertion on `s.disp` to an unexported recorder interface the real engine implements; `noopDispatcher` and the test spies record nothing. It runs on a fresh detached context with a 5 s bound, on both the `Run` and the `Start` paths.
  - every `jobs.JobRepository` fake gains the method. If `/decompose` finds S5 oversized, it splits into (a) `jobs`, `store` and the migration and (b) the layer and rendering.
  - in `Start` this happens before `Done` closes, so a waited call already shows it.
  - if that write fails too, both failures are logged (`job_id`, never arguments).
- `RenderedJob` gains `OutcomeAuditFailure *{At, Reason}`. `Reason` is a fixed, Relay-authored `jobs` constant: the Tasks ran, the trail holds the intent but not these outcomes, and the cause is in the Relay's error log. It never carries the store's error text.
- The field appears as `outcome_audit_failure` (omitempty) on:
  - MCP `ExecutionOutput` and `RunOrPlanOutput`.
  - Control API `executionResponse` and `jobResponse`.
  - MCP golden outputs and OpenAPI follow.
- Threat model R57 replaces "only the Relay's own error log records the failure (EX-68)" and drops "designed".

**S6, EX-60** (`mcp/tools_operations.go`, threat model):
- One sentence appended to the `list_operations` Description.
- R55 drops "designed" from "(EX-60, designed)".

## Constraints

- **Invariant 10:**
  - S3 and S4 move each decision into the layer and keep no adapter pre-check behind.
  - The MCP schema stops enforcing `argv` presence, the key length and the timeout bounds. The go-sdk validates input before the handler runs (go-sdk v1.8.0, `applySchema`), so an enforced bound would be a refusal made by the adapter, unaudited.
  - `wait_seconds` keeps its schema bounds and `ResolveWaitSeconds` on both surfaces: how long a call waits is the adapter's (EX-69, owner decision 2026-11-16). It decides nothing about what may run.
  - EX-69 also leaves an adapter free to refuse a field outside its declared bounds. S3 and S4 still drop the MCP schema bounds on `argv`, the key length and the timeout, because the layer now decides each of them (EX-67, the key store's `IdempotencyKeyError`, EX-59) and one decision site keeps the refusal audited.
  - The `Idempotency-Key` header and the multiple-value 400 are transport decoding.
- **Invariant 4, ADR-0054 §2 and §8:**
  - `Start` commits the Job, its Tasks and the dispatch intent before it returns, and its fan-out runs on a detached context. Returning early or a dropped connection therefore never cancels or repeats a Task.
  - EX-57 ships only with EX-58, so a lost response always has a safe retry.
  - Keys go only through the layer's key store; a repeat is never inferred from request content.
- **Invariants 5 and 13:** the call-shape refusals sit before the cap. The risk class is still fixed in `resolveAction`, and no adapter sets one.
- **Invariant 12, ADR-0011:**
  - The checks look at names, presence and a number only; argument values stay the daemon's.
  - A preflight refuses a call that cannot be asked at all (PF-13), and still reports its guardrails in `would_be_rejected`.
- **Invariant 11, ADR-0054 §9:** the 300 s ceiling and the 24 h window are constants, not settings.
- **Invariants 8 and 14:** `TaskRequest.timeout_seconds` and the daemon's clamp are unchanged.
- **ADR-0025:** a keyed re-attach is an audited read and fails closed, as today. `outcome_audit_failure` rides `get_job`'s existing audited read.
- **ADR-0027, AP-77:** the first Control API re-drive after an approval dispatches through `Start` and may wait; a later re-drive of the released approval re-attaches and never waits. `HashPlan`'s reliance on validated Native names holds, because the EX-61 stage precedes the approval gate.
- **ADR-0052:** the Console is not touched. EX-66 names `get_job` and the Jobs route only.

## Rejected

- **EX-57 as its own issue ahead of EX-58.** A lost response would have no safe retry.
- **EX-58 as its own issue ahead of EX-57.** Accepting the key needs `Start`, and a Control API on `Start` with a full wait already moves its failed outcome write from reported to logged (EX-68), so the pair would change behaviour mid-milestone without the hand-back that justifies it.
- **EX-66 inside S2.** It needs a migration and touches the layer and both read paths. S2 is already the milestone's largest step.
- **A Control API default `wait_seconds` above 0.** The wait is optional (EX-57) and defaults to 0 on MCP (EX-35). A hidden default wait widens the lost-response window for every caller.
- **202 for a running Job.** 202 means `pending_approval`, and clients branch on it.
- **Keeping the adapter pre-checks, or the schema bounds, as defence in depth.** Each would be a second decision site, which is the invariant-10 defect itself.
- **Running the call-shape refusals before the zero-match refusal on a real dispatch.** EX-64, EX-67 and EX-59 place them at EX-61's stage (EX-3). Only Plan acts on them whatever matched, because PF-13 says so.
- **A dedicated empty-argv error type.** `MalformedCallError` already renders on both surfaces. The Control API title becomes "invalid operation request", and OpenAPI documents it.
- **Holding the outcome-write failure in memory, or storing the store's error text.** Memory is lost on restart, and the error text may carry internals. The fixed reason and the log are enough.
- **Clamping a timeout above 300 silently.** ADR-0054 §9.
- **Deriving `MaxWaitSeconds` from the timeout ceiling.** EX-35 and EX-59 are separate claims that happen to share 300.
- **Deleting `Execution.Run`.** No claim needs it, and the devharness uses it.
- **Accepting the key as a body field as well as the header.** EX-58 names the header.
- **Surface-specific idempotency error text.** The layer's text says "Poll get_job". The Control API renders it verbatim, and OpenAPI says that is `GET /api/v1/jobs/{id}`. One text keeps the parity test exact.
- **A compatibility switch for blocking clients.** Pre-release; the response change ships with OpenAPI and `STATUS.md`.
- **The secret warning on `run_operation` and `raw_exec` too.** EX-60 names `list_operations`; widen by spec, not by plan.

## Open

- **Other adapter-side input refusals.** An empty `operation` and an unparseable Selector stay at the adapter, as EX-69 allows. Not part of S3.
- **Follow-ups for `/spec-author`:** S4 refuses a negative timeout in the layer, which EX-59 ("above 300") does not name, and `TimeoutError`'s text should read sensibly for it; S3 and S4 make Plan refuse an empty argv and an over-ceiling timeout, which `policy-preflight.md`'s Refusals table does not list.
- **EX-3's stage name.** EX-3 calls the stage "the Template refusals (EX-51, EX-61)". After S3 and S4 it also holds the call-shape checks. The wording becomes imprecise, not untrue; fixing it is for `/spec-author` or `/milestone-close`.
- **Recorded, no action:**
  - A keyed Job created before the upgrade with a timeout above 300 and re-issued within 24 h re-attaches rather than being refused. The key lookup precedes the stage (EX-3) and nothing is dispatched.
  - A `timeout_seconds` outside int32 is a decode error at the adapter, not a dispatch request.
