# v0.7.0 — Admin Console: Administration & Execution

**Spec:** `docs/specs/approval.md` — **AP-60 … AP-71** (the round trip).
**Milestone:** v0.7.0 — Admin Console: Administration & Execution   **Opened:** 2026-09-24
**Scope of this plan:** #646 only — MRTR elicitation for in-band approval. **Built:** #646 closed
on 2026-10-06, and the composition root enables the answer path (S4b). v0.7.0 carries other
issues; if another slice of it is designed, it is appended here rather than filed as a second
plan, because `/milestone-close v0.7.0` deletes this file.

**Settled by the owner:**

- **Precedence with the MCP task handle** (2026-09-24) — **elicitation wins.** A park that emits
  an answerable question emits no task envelope (ADR-0028 amendment, #715).
- **No origin check** (2026-09-25, ADR-0040 as amended). ADR-0040's strict separation — the
  surface that created a request answers it — was withdrawn before it was built, for its
  availability cost: every rule stricter than self-confirmation in-band would have left an
  MCP-originated request undecidable. AP-74 … AP-76 are retired unbuilt.
- **MCP is the approved pathway** for agent-originated approval; Gleipnir is where the human is
  expected to answer. The Control API decides any parked request and is the rescue, not relied
  on. The Console's approval surface is removed by ADR-0044 (`approval.md` AP-80, outside this
  plan). Out-of-band as a rule *requirement* stays shelved in
  the private roadmap (`roadmap: relay/out-of-band-approval`), pending the permissions rework (#716).
- **Recorded, not solved here** (both in the private roadmap): a restart strands an in-flight
  MRTR answer (see *Open*), and whether "answered over MCP" binds any MCP Account or only the
  exact client that asked.

## Intent

A gated MCP dispatch under an `in-band` rule today answers `tools/call` with a `pending_approval`
result and stops: a human must be reached out of band and the model told to re-drive. This plan
makes Relay answer that call with an **MRTR input-required result** (SEP-2322, MCP 2026-07-28)
carrying a Relay-authored approval question, and accept the human's answer on the client's retry of
the *same* call — decided on the same capability-layer path as `approve_request`, from the same
single file the decision guard exempts (ADR-0029 decisions 5 and 6).

Nothing about *who may decide*, *what a decision means*, or *what a channel is worth* changes. One
decision model, a second delivery envelope.

## Claims

The twelve behaviours this plan promotes are `approval.md` **AP-60 … AP-71**, migrated in #715.
The in-band honesty residual is threat-model R21 (it covers the responder assertion); the
concurrent-retry residual is R24.

## Shape

### Seams that do not move

- **`capability.Service.DecideApproval`** stays the one place a decision is recorded. The MRTR answer
  calls it, from `tools_approval.go`, with the same `ChannelInBand` constant and the same asserted
  approver in `capability.Assertions.OnBehalfOf`. No new capability-layer decision entry point.
- **`capability.Service.Run`** stays the one dispatch path. The retry re-enters it whole — Freeze,
  Selector resolution, `Authorize`, blast cap, `checkApproval`'s plan-hash match — because the answer
  is recorded *before* `Run` is called, never threaded into it.
- **`Stateless: true, JSONResponse: true`**, and no server-initiated `elicitation/create`. MRTR is
  chosen precisely because it needs neither.
- **`/proto` is not touched.** MCP result shapes are JSON-RPC, not the daemon wire contract. No
  contract step, no proto gate.

### The emission predicate

A question is emitted **only** when all of these hold:

1. **An approval decider is wired** (`WithApprovalDecider`) **and elicitation is enabled at the
   composition root.** No decider, no enablement → no question. Relay never asks a question it
   cannot accept an answer to.
2. **The SDK itself would judge this client MRTR-capable.** Read exactly what
   `clientSupportsMultiRoundTrip` reads: the **session's** initialize params — capable when they are
   nil, or when their protocol version is ≥ 2026-07-28.
3. **The per-request `_meta` agrees**: `io.modelcontextprotocol/protocolVersion` ≥ 2026-07-28 and
   `io.modelcontextprotocol/clientCapabilities` carries `elicitation`, via `ServerRequest`'s accessors.
4. **The park is askable** — the capability layer's boolean (next section).

> **Why 2 and 3 are both required, and why 2 is the one that must not be skipped.** These are two
> *different* client-controlled values that can disagree. The session's initialize params are
> synthesized from the **`MCP-Protocol-Version` HTTP header**; the per-request `_meta` is the
> SEP-2575 triple in the JSON-RPC body. A client sending a modern `_meta` with an absent or legacy
> header gets initialize params synthesized at the legacy version — the params are then already
> non-nil, so the SDK never upgrades them — and `clientSupportsMultiRoundTrip` returns **false**
> while conditions 3 and 4 return true. `sdkmcp.NewServer` installs `serverMultiRoundTripMiddleware`
> unconditionally, and on that path it fulfils `InputRequests` by calling the client back with a
> **server-initiated `elicitation/create`** — the pattern ADR-0029 rejected, on a stateless handler
> that cannot serve it. Mirroring the SDK's own predicate is what keeps that branch unreachable.
> The header-versus-metadata mismatch gets its own end-to-end case.

### What "askable" means, and who decides it

The capability layer computes it at `checkApproval`, where it holds the Requirement and the calling
Principal together. A park is askable when **all** hold:

- the rule's channel is satisfiable in-band;
- the rule does **not** exclude the requester — an in-band answer is authenticated as the requesting
  session's Account, so a requester-excluded rule refuses it unconditionally;
- the rule's audience admits that Account — an audience that does not name it refuses too;
- **the park was created by this call**, not bounced off one already pending.

The role floor needs no term: the caller already passed `Authorize` for this Action, and the decision
floor is *the same floor the Action needed to be requested*. A test pins that rather than leaving it
as reasoning.

**Why all four, and not just the channel.** Asking a question whose answer is refused by
construction manufactures exactly the approval fatigue `approval.md`'s *Purpose* names as a security
property, and a permission ask is never replayed client-side, so every one of them reaches a person.
The last term is the capability layer's own rule restated: it already declines to re-notify on a
re-drive (`NotifyParked` fires only for a created park), and a question is a page.

**A partial quorum falls out correctly.** Under `count: 2`, an in-band answer is recorded as one
approval and the request stays pending; the retry then re-enters, finds it pending-not-created, and
renders `pending_approval`. No loop, no second question, and the honest partial is recorded.

### `requestState`: what it binds, and what it is worth

Sealed fields: **format version, the calling Account's ID, the approval request ID, the plan hash,
the tool name, a digest of the call's arguments, and an absolute expiry** (the parked Request's
`ExpiresAt`, never an independent clock). HMAC-SHA256, versioned prefix, constant-time compare,
bounded far under Gleipnir's 16 KiB limit.

**The seal is load-bearing, not defence in depth, and the plan says so.** The decision is recorded
*before* anything is re-resolved, so at decision time the only thing binding the answer to a
request is the seal:

| Attack | Refused by |
|---|---|
| Tampered state | The seal alone |
| **Cross-request** — answer request A's question against request B | **The seal alone**: the sealed request ID is what the decision cites |
| **Plan binding at decision time** | **The seal alone**, plus `Request.Decide`'s own `ErrPlanChanged` against the sealed hash |
| Cross-account | The seal alone |
| Replayed onto a different call | The seal alone (tool name, args digest) |
| Expired | The seal, and `Request.Decide`'s `ErrNotPending` |
| Fleet changed since the question | **Re-derived**: `Run` recomputes the plan hash; a mismatch finds no approved request, so the dispatch re-parks |

Only the last row is re-derived, and it is the one that matters for *execution*: a broken seal can
never make unapproved work run, because release still turns on a freshly computed plan hash. What a
broken seal could do is let the calling session record a decision against a request of its choosing —
which is why the seal, not the pipeline, is the control there.

**Read against `approve_request`, this is stricter, not weaker.** That tool accepts any
`request_id`/`plan_hash`/`approver` the session cares to send, with no binding at all; ADR-0029
accepted that as the client-integrity assumption. MRTR narrows it to *the question Relay actually
asked this caller*. The residual risk of a lying client is unchanged and already accepted (R21).

**Where the key comes from, and invariant 11.** Minted by `crypto/rand` inside `mcp.New`, once per
process, **never configuration** — the `consoleauth` CSRF-pepper precedent, for the same reason.
There is nothing to configure, so there is no code path from a request to it and nothing to appear
in a process listing or crash dump; invariant 11 holds by construction. It bounds nothing about who
may authenticate. **Cost:** a restart, or a retry landing on another replica behind a load balancer,
invalidates an outstanding state. That fails **closed** — the answer is refused, the request stays
pending, `approve_request` and `/api/v1` still answer it — and the result's `_meta` carries the
request ID and plan hash so that fallback is reachable programmatically. That fallback is the
**rescue**, not the approved pathway (ADR-0040 as amended), and AP-62 means the client is not asked
again, so a restart mid-decision strands the request until a human rescues it or its TTL expires.
See *Open*.

### The answered retry, in order

1. Open and verify `requestState`; cross-check tool name, args digest and account.
2. Require **exactly one** `inputResponses` entry, keyed by the sealed request ID.
3. Require a **responder assertion** with `gate == "permission"`. Take **`username`** as the asserted
   identity — `approve_request`'s `approver` is a human-legible string and the asserted lane is
   rendered to auditors — and validate it at this boundary with `audit.ValidateAsserted`'s rule:
   ≤ 256 bytes, no control characters, **refuse rather than truncate**. *(That validation exists
   today only on the `X-Relay-On-Behalf-Of` header lane; `approve_request`'s `approver` bypasses it,
   so S4a fixes both in the one file.)* An empty or whitespace-only value is no assertion and
   collapses into the machine-self-decision refusal.
4. Set the assertion on the context's `Assertions` — the same lane `approve_request` uses — and call
   the exempt file's helper: `accept` → approve, `decline` → deny.
5. Branch on the outcome, using the current Request the capability layer now returns:

   | Outcome | Response |
   |---|---|
   | Approved, no Job bound | Call `Run` **once**. Full pipeline. If the fleet moved, the hash differs, nothing matches, the dispatch **re-parks** — and, being a created park, asks afresh. |
   | Approved, Job already bound | **Re-attach**: render that Job's results. No second dispatch. |
   | Denied | Terminal. `Run` is never called. The denial is the tool result. |
   | Expired / not pending because it lapsed | Treat the answer as spent; run the pipeline, which re-parks and asks afresh. |
   | Still pending (partial quorum) | `pending_approval`. No dispatch, no new question. |
   | **Requester excluded** | Render `renderApprovalError`'s existing message: a second person must answer out-of-band. |
   | **Not in audience** | Its existing message: this Account is outside the audience. |
   | **Machine self-decision** (no responder, `gate: "information"`, `io.gleipnir/replayed-from`, `cancel`) | Its existing message, naming the missing human. |
   | **Weak channel** (a race against a reloaded rule) | Its existing message: answer on the Control API endpoint. |

6. Every one of these is an ordinary tool **result**, never a tool error, for the reason
   `PendingApprovalOutput`'s doc already gives about teaching an agent that a gate is a breakage.

**Why decide before dispatching.** If the pipeline ran first, a `decline` would arrive after the work
had executed. Deciding first also binds the answer to the request and plan hash the human was
*shown*, which `Request.Decide`'s `ErrPlanChanged` already enforces, and leaves the re-drive as the
ordinary re-drive `approve_request` has always relied on. This is *observe the park, decide,
re-drive* collapsed into one tool call, every step crossing the seams it crosses today.

### Precedence, and the task handle it leaves behind

**Elicitation wins.** A park that emits a question emits no task envelope; a Tasks-capable client
that cannot be asked is unchanged. (The Tasks shim would already pass an input-required result
through untouched — it keys off `structuredContent.pending_approval`, which such a result does not
carry — so this step turns an accident into a decision with a test.)

**One consequence, stated:** the capability layer mints a task handle for every park, so an
MRTR-answered park leaves an **orphan handle** that no client is told about and that expires on its
own TTL. Harmless — a handle is a poll handle and decides nothing — and not worth a conditional in
`Service.Run`; recorded so nobody reads it later as a leak.

## Constraints

- **Invariant 10 — one capability layer; adapters narrow only.** The surface supplies three facts and
  decides nothing: who was authenticated, what they answered, and that it arrived in-band. Channel
  strength, audience, requester exclusion and the created/observed distinction are all computed in
  `capability`, which is why `ParkedError` gains a boolean rather than the adapter reading a
  Requirement. `no_dispatch` holds unchanged.
- **Invariant 11.** The seal key is not configuration, so there is nothing to reach from an API.
- **Invariant 4 — at-most-once.** The re-attach branch is the answer *for an answered retry*. The
  daemon's Task-ID dedup — the actual subject of invariant 4 — is untouched. What this plan does not
  close is **#713**, a second Job on a later re-drive (threat-model R24), fixed outside this plan
  by PR #752.
- **Invariant 12.** Untouched: nothing here evaluates Policy.
- **ADR-0029 decision 5 — the guard is narrowed, not removed. No amendment is needed.** The answer
  arrives on a `run_operation`/`raw_exec` retry, whose handler is in `tools_execution.go`; that
  handler calls a helper **defined in `tools_approval.go`**, and only that helper names a decision
  identifier. The guard matches identifiers by exact name, so the helper must simply not be called
  `DecideApproval`/`RecordDecision`/`ApprovalDecision`/`Channel*`, and `ApprovalDecisionOutput` does
  not collide.
  **What the guard does and does not prove, stated plainly:** it proves only that no forbidden
  *identifier* appears outside one file. It cannot prove that the *acceptance logic* — the responder
  rule, the seal check, the branch table — lives there. Putting that logic in `tools_approval.go` is
  therefore a choice, not something enforcement makes true, **and the placement is the point**:
  ADR-0029 decision 5's promise is that a reviewer can audit the whole of this hole by opening one
  file, and that promise is kept by what is written in the file, not by the AST scan.
- **ADR-0029 decision 6, and decisions 1–4.** This is decision 6, built. `approve_request` stays;
  attribution stays verified-requester/asserted-approver; `ErrMachineSelfDecision` stays relaxed only
  for an in-band answer *carrying* an assertion; `ErrWeakChannel` is untouched.
- **ADR-0028 — `tasks/update` stays out of scope; its amendment is done (#715).** The boundary
  holds: an answer arrives on a retried `tools/call`, never on `tasks/update`, and the guard's
  literal-string ban stays. Its old premise — *"Relay emits no `inputRequests`"* — was replaced
  before this plan builds anything that falsifies it: ADR-0029 settled the question, S2 makes Relay
  emit them, and the boundary now rests on the precedence decision (**an elicited park emits no
  task envelope, so no client holds both a handle and a question for the same park**).
- **ADR-0027.** Unchanged by this plan; its amendment log already anticipates MRTR.
- **ADR-0040, as amended 2026-09-25.** Nothing here enforces origin. MCP is the approved pathway
  and this plan makes it answerable in-band; the rescue path keeps deciding any parked request,
  and S6 keeps that proven.
- **Gleipnir is a consumer of Relay, never a component (AGENTS.md, ADR-0016).** Honoured on the emit
  side: the question is made consent-shaped by the **protocol-generic** rule — a `requestedSchema`
  with no properties — not by emitting a vendor `elicitation-kind` hint. It cannot be honoured on the
  accept side; see *Needs a human*.

## Rejected

- **Thread the answer into `Service.Run`.** Puts elicitation vocabulary in the capability layer and
  creates a second decision location; fails ADR-0029 decision 5.
- **Dispatch first, then record the answer.** A `decline` would arrive after the work ran.
- **Server-initiated `elicitation/create`.** Removed by 2026-07-28, costs the stateless property;
  already rejected by ADR-0029.
- **Trust the SDK's middleware to handle non-MRTR clients.** It attempts exactly that
  server-initiated elicitation.
- **Gate emission on the per-request `_meta` alone.** The SDK gates on a different, independently
  client-controlled value; see the emission predicate.
- **Emit on the rule's channel alone.** Manufactures approval fatigue for requester-excluded and
  audience-restricted rules, whose answers are refused by construction.
- **Emit on every re-drive.** Re-pages a human per poll; contradicts the capability layer's own
  no-re-notify rule.
- **A root-owned seal-key file now.** The right mechanism if cross-replica retries must survive, but
  it adds a security-floor configuration surface for a property the design does not need.
- **Carrying the approver in `requestedSchema`.** Turns the consent prompt into an information form
  and asks a human to type an identity; explicitly refused by the client contract.
- **Emitting a vendor `elicitation-kind` hint.** Couples Relay's output to one client; the structural
  rule achieves the same.
- **Minting a task handle *and* a question.** Two envelopes for one park, with no client asking.

**Not rejected — filed.** "Make every re-drive of an approved plan re-attach" is not a design
choice but the fix for a pre-existing defect, **#713** (fixed by PR #752). This plan's narrow
re-attachment, scoped to an *answered* retry, neither depends on it nor substitutes for it.

## Open

- **Restarts, and retries on another replica, strand an in-flight answer.** A process-lifetime seal
  key means a retry after a restart, or on a different replica behind a load balancer, is refused
  (fail-closed) — and because a re-drive of an already-pending request re-pages nobody (claim 3,
  AP-62), the client is never asked again and the request waits for its TTL unless a human rescues
  it on the Control API. **The owner chose not to solve this in v0.7.0**; it is recorded, with the
  two candidate fixes (re-ask when the state is stale; persist the key in the store) and neither
  chosen, in the private roadmap (`roadmap: relay/out-of-band-approval`), and as threat-model R27. It is tolerable only
  because the rescue exists.
- **A pending request can never be re-asked.** Claim 3 means that once a request is pending, no later
  session is offered the question — including after a client timed out without answering. That is the
  no-re-page rule applied honestly, and it may prove too strict in the demo. Surfacing it as a known
  edge rather than tuning it blind.
- **Gleipnir's per-call timeout.** An approving retry dispatches and blocks on the daemon inside
  `GLEIPNIR_MCP_TIMEOUT` (30 s default, 120 s in the demo). No Relay change; an operational note.
- **The question text carries agent-chosen arguments.** `Summary` is Relay-authored but includes the
  Operation's arguments — already true of the webhook and the Console. Gleipnir renders it as
  untrusted plain text attributed to the server. No new control proposed; one line in *Accepted
  residual risk*.

## Needs a human

Settled as #646 was built: the `approval.md` migration and the ADR-0028 amendment (#715); the
sealing package sited under `controlplane/mcp/requeststate`, already on the security surface;
#713 (PR #752); and ADR-0040's trade, now threat-model R26. Two points stay worth knowing:

1. **A vendor-namespaced key is Relay's acceptance rule.** An answer is a decision only when the
   response `_meta` carries a responder assertion with `gate == "permission"`, and
   `io.gleipnir/responder` is the only such form that exists. That makes the MRTR in-band path
   **Gleipnir-only in practice**: any other MRTR client's `accept` is refused as a machine
   self-decision — fail-closed, but a coupling to a consumer. And the `permission` gate is a
   client self-report of the same strength as `approve_request`'s `approver` string: it buys
   **interoperability discipline, not verification**. The rule is framed as *"a responder
   assertion, of which the Gleipnir key is the one recognised form today"*, so a standard key is
   additive (AP-64; AP-79 adds the OAuth-session path).
2. **The rescue is accepted availability** (owner, 2026-09-25). Do not narrow it as a tidy-up.

**Does anything here make a claim in a migrated spec untrue? No.** `approval.md` is migrated
(#715), and this plan promotes **AP-60 … AP-71** from *Designed, not built* and nothing else. No
step makes a built claim untrue; the near misses, checked one by one:

- **AP-2** (a park leaves no Job and no Tasks) — preserved by construction; AP-60 restates it for
  the question.
- **AP-15, AP-18** (two decision paths, and no third) — the MRTR answer is the in-band path through
  the requesting client, the same path `approve_request` is; no third route.
- **AP-16, AP-17, AP-19** (the Console and Control API decide) — untouched by this plan, and S6
  kept them proven as the rescue. ADR-0044 since retired AP-16 and AP-19 in favour of AP-80 (the
  Control API decision endpoint only).
- **AP-28** (deciding does not itself dispatch) — still true: `DecideApproval` records the decision
  and returns; the retry then calls `Run`, which is an ordinary re-drive. One tool call carries both,
  but the decision does not dispatch.
- **AP-41** (a park is audited as created or observed) — unchanged; the askable boolean reads the
  same distinction and does not alter it.
- **AP-70** (a client that cannot be asked sees no change) — this is the claim every dark step and
  the S4b flip exist to protect.
