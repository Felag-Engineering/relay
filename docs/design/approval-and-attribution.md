# Approval & Attribution — design note

**Status:** planning-session output (owner + AI-agent, 2026-08-07), pre-ADR. This note is the
grounding brief for the approval-callout ADR (#268) and the scope inputs it produced for
#209, #276, #285, and the Accounts milestone. It records decisions and their reasoning; the
ADR is where they become binding.

## The problem

Two forensic questions the audit trail must answer, with the trust level of each answer
explicit:

1. **Who told the agent to do this?** (attribution of the request)
2. **Who authorized it?** (attribution of the approval)

Today every action attributes to the single seeded credential; reads are not audited at
all. The design below layers identity, asserted context, and human approval so both
questions are answerable — and so an auditor can tell which parts of the answer Relay
*verified* and which parts were merely *claimed*.

## Identity model

- **Accounts** (the Accounts & Access milestone, ADR-0010): human and machine Accounts
  with roles. Machine-identity creation is Account CRUD — an admin creates a machine
  Account (e.g. `gleipnir-prod`) and mints its revocable API token. Already in scope.
- **OAuth 2.1 resource server on the MCP endpoint** (scope addition to the Accounts
  milestone): MCP's standard authorization layer has the client obtain its token through
  a flow a human completes. A human connecting their own harness (e.g. Claude) therefore
  yields a **per-human authenticated session** using off-the-shelf harness support — no
  custom protocol. Static machine tokens remain for headless/CI drivers. This is the
  standards-based answer to "which human's authority is this session operating under."
- **Teams** ("the ops team"): v1 is a free-form **asserted** string in `on_behalf_of` —
  cheap, honest about its trust level. Direction: once OIDC lands for Console login,
  federate groups from the IdP (a team is an IdP group claim, recorded and used for
  approval-audience routing). Relay never grows a native org chart.

## The attribution triple

Every gated dispatch carries three identities, in two structurally distinct lanes:

| Field | Example | Lane |
|---|---|---|
| `requested_by` | `gleipnir-prod` (machine token) or `mike` (OAuth session) | **verified** — Relay authenticated it |
| `on_behalf_of` | `ops-team`, session id, ticket/change ref, traceparent | **asserted** — the caller claimed it (#276) |
| `approved_by` / `confirmed_by` | `mike` (+ channel, plan-hash) | **verified** — authenticated decision |

**Schema rule:** the audit record structure must distinguish the verified lane from the
asserted lane. Blurring them is how audit trails become fiction — a jailbroken agent can
assert anything, but it cannot forge the verified fields. The asserted lane is still
valuable: for an honest orchestrator it is the join key back to the harness's own session
logs, where the literal instruction lives (the prompt never crosses the MCP boundary; only
tool calls do).

## The key insight: sessions authorize, surfaces bind intent

An OAuth session through MCP proves a human authorized the **session** — not that a human
intended each **call**. The tool calls are still generated by a model, and the session can
be steered by prompt injection in content the model read (see #274, #283). Therefore:

> **MCP-originated calls are agent-grade regardless of whose identity authorizes the
> session.** The discriminating axis for gating is not human-vs-machine principal but how
> strongly the originating surface binds a human's intent to the individual action.

The Console's step-up apply and the CLI's `--apply` bind *this human confirmed this
specific Plan*; an MCP session cannot. This is also the honest justification for the
Console execution surface (#264): its apply flow carries the strongest intent-binding in
the system — which is why its browser security (CSRF/XSS) sits on the most dangerous path.

## One approval mechanism, many delivery surfaces

The invariant, everywhere:

> **An authenticated human, on a channel able to carry their decision, confirms a
> Relay-authored Plan.**

- The Job parks in `pending-approval` (Job-engine state, gate config root-owned — the
  milestone's [2/6] issue).
- **Relay authors the approval content** — operation, arguments, resolved fan-out,
  per-Node plan verdicts, requester, on-behalf-of claim — so the agent/harness cannot
  truncate or spin what the approver sees.
- **Delivery** is elicitation (held, or nested in an MCP task handle) or webhook — the
  [3/6]–[5/6] issues. Design posture: **assume elicitation delivers correctly** (the spec
  obligates clients to present it to the user; it is the interop bet the UX rides on) and
  make it the primary, first-class channel.
- **Decision channel strength is configurable per gate rule** (see grammar below):
  - `in-band` — the elicitation answer itself is the decision. Zero friction; trusts the
    harness.
  - `out-of-band` — the decision must land on the authenticated decision endpoint (the
    [3/6] issue): Console approval queue, CLI, or a link the elicitation carries.
    Rationale for offering this tier: the requesting harness holds the session's
    credential, so an in-band answer is only as trustworthy as the harness; the
    out-of-band decision rides a **credential the agent session does not hold** (browser
    session + step-up re-auth / passkey). The difference is "the approval is an assumption
    about the client" vs "the approval is evidence."
  - Suggested defaults: self-confirmation rung in-band; second-person rung out-of-band.
    Deployments move the dial either way in root-owned config.

## The confirmation ladder

Gate rules select a rung; rungs differ only in who must answer and how strongly:

1. **No gate** — below thresholds; runs immediately.
2. **Self-confirmation** — "are you sure you wanna drop prod." Audience is the requester
   themselves; they see the Relay-authored Plan and confirm. Human requesters only —
   an agent cannot confirm itself, so machine requesters' minimum gated rung is 3.
   The Console/CLI step-up-apply flow **is** rung 2 fused into the request surface, not a
   bypass of it.
3. **Second-person approval** — audience excludes the requester (`requester_allowed:
   false`). The two-person tier.

## Gate rule grammar

Root-owned Relay config (file-only, above the AI's reach, narrows-only — consistent with
the blast-cap precedent and invariant #11):

```
match:       risk class · blast size · selector namespace · principal (type/Account) · operation
requirement: count · audience · requester_allowed · channel (in-band|out-of-band) · ttl
```

- **Quorum (`count`)**: v1 config exposes `1` or `2`. The **stored schema is
  requirement-vs-set-of-decisions from day one** (the Job-stages precedent: model the
  general shape, expose the narrow config), so N-of-M and richer rules land later without
  a data migration. Each decision is its own audit record (approver, timestamp,
  plan-hash, channel). Partial state (`1 of 2`) is visible in the approval queue; the
  second approver sees who already signed — itself a fatigue mitigation.
- **Arbitrary rules later**: richer matching ("2-of-`sre-leads` for mutate over 50 Nodes
  on `relay:env=prod`") is a config-language upgrade over the same schema. #285's Cedar
  evaluation should cover **both** Grants and approval rules — same genre of policy; do
  not hand-roll two mini-engines.
- **`requester_allowed`** enables separation of duties (`approved_by ≠ requested_by`) —
  only meaningful because both identities are verified.
- **`ttl`**: parked Jobs expire; an approval against plan-hash `abc123` is not redeemable
  indefinitely.

## Plan-hash binding and drift

An approval binds to a **content-addressed Plan** — operation, arguments, and *resolved
fan-out* — not to "the Job in the abstract." Dispatch executes only if the Plan still
matches at dispatch time; material drift (registry changes altering the fan-out) re-parks
the Job for re-approval. This closes the park-something-innocuous-then-mutate-the-world
gap and is the approval-flow analog of ADR-0011's plan-verdicts-match-execution property.

## Batch and window approvals (fatigue)

"The ops team is doing a bunch of work" must not mean forty elicitations. An approval may
cover a **declared batch** (a set of Jobs) or a **scoped window** ("mutate-class against
`service=web`, next 2 hours, requested by `gleipnir-prod` for ops-team") — approved once,
every covered Job auditing back to the same approval ID. Bounded in scope and time, this
is a *time-boxed narrowing grant*: philosophically consistent with the deferred Grants
rule (approvals narrow what is possible; they never widen Policy). First-class in the ADR
and the approval-record schema, not a bolt-on — rubber-stamping is the failure mode the
whole mechanism exists to prevent (see the fatigue scope note on #268).

## Worked example

Gleipnir (machine Account `gleipnir-prod`) dispatches a mutate batch with
`on_behalf_of: ops-team, change: TICKET-123`. The gate rule (mutate + blast > N) parks
the Jobs, `count: 1, requester_allowed: false, channel: out-of-band`. The callout is
delivered via elicitation inside the MCP task handle; Gleipnir's audience router reaches
Mike. Mike opens the link, authenticates (Console session + step-up), reviews the
Relay-authored Plan, approves. Audit answers both questions in one query:
`requested_by: gleipnir-prod ✓ · on_behalf_of: ops-team ⚠ · approved_by: mike ✓
(out-of-band, plan-hash …)`.

## Impact on planned work

- **Approval-callout milestone / #268 (ADR)**: must specify the attribution triple,
  plan-hash binding + drift re-park, the confirmation ladder, quorum schema
  (requirement-vs-decisions), channel strength, batch/window approvals, TTL, and the
  requester-exclusion knob.
- **Accounts milestone (v0.3.0 in the pre-resequence numbering)**: + OAuth 2.1
  resource-server support on the MCP endpoint; + the asserted `on_behalf_of` lane in the
  audit schema; teams-as-asserted-string with IdP federation named as direction.
- **#209 (Gleipnir integration)**: the audience-routing contract — Relay's gate config
  defines *who may approve*; Gleipnir defines *how they are reached*. Delegation-model
  decision (shared machine Account + asserted context vs per-user tokens) is largely
  resolved by the OAuth option: OAuth sessions for interactive humans, machine Accounts
  for headless, `on_behalf_of` for the rest.
- **#276**: extend from bare traceparent to the structured asserted lane.
- **#285 (Cedar)**: evaluate against the approval-rule grammar as well as Grants.
- **#264 (Console execution ADR)**: the intent-binding framing above is the justification
  and the guardrail spec (step-up apply = rung 2; strict deployments set mutate rules to
  rung 3 even for Console requests).

## Open questions

- Decision-endpoint auth for approvers who are *not* Console users (pure-API shops):
  what carries the disjoint credential — a short-lived signed link, a CLI step-up, both?
- Does the approval queue live only in the Console, or does the read-side API expose it
  for external approval UIs (Slack-bot approvals via #277-style integrations)?
- Read auditing (dispatch-only today) — tracked as its own decision issue; the asserted
  lane should apply to read audit records too if/when they exist.
