## The problem

The audit trail must answer two forensic questions, and say how far each answer can be
trusted:

1. **Who told the AI-agent to do this?** (attribution of the request)
2. **Who authorized it?** (attribution of the approval)

The design layers identity, asserted context and human approval so both are answerable, and
so an auditor can tell what Relay *verified* from what was merely *claimed*.

## Identity model

- **Accounts** (ADR-0010): human and machine Accounts with roles. An admin creates a machine
  Account (e.g. `gleipnir-prod`) and mints its revocable API Token.
- **OAuth 2.1 resource server on the MCP endpoint** (ADR-0024): a human connecting their own
  harness completes the token flow, which yields a **per-human authenticated session** with
  off-the-shelf harness support. Static machine tokens remain for headless drivers.
- **Teams** ("the ops team"): a free-form **asserted** string in `on_behalf_of`. The
  direction is to federate groups from the IdP; Relay never grows a native org chart.

## The attribution triple

Every gated dispatch carries three identities, in two structurally distinct lanes:

| Field | Example | Lane |
|---|---|---|
| `requested_by` | `gleipnir-prod` (machine token) or `mike` (OAuth session) | **verified** — Relay authenticated it |
| `on_behalf_of` | `ops-team`, session id, ticket/change ref, traceparent | **asserted** — the caller claimed it (#276) |
| `approved_by` / `confirmed_by` | `mike` (+ channel, plan-hash) | **verified** — authenticated decision |

**Schema rule:** the audit record must keep the verified lane apart from the asserted lane.
A jailbroken AI-agent can assert anything, but cannot forge the verified fields. The asserted
lane still matters: for an honest orchestrator it is the join key back to the harness's own
session logs, where the literal instruction lives (the prompt never crosses the MCP boundary;
only tool calls do).

## The key insight: sessions authorize, surfaces bind intent

An OAuth session through MCP proves a human authorized the **session** — not that a human
intended each **call**. The tool calls are still generated by a model, and the session can
be steered by prompt injection in content the model read (see #274, #283). Therefore:

> **MCP-originated calls are agent-grade regardless of whose identity authorizes the
> session.** The discriminating axis for gating is not human-vs-machine principal but how
> strongly the originating surface binds a human's intent to the individual action.

The Console's step-up apply binds *this human confirmed this specific Plan*; an MCP session
cannot. That is the honest justification for the Console execution surface (ADR-0026), and
the reason its browser security (CSRF/XSS) sits on the most dangerous path.

## One approval mechanism, many delivery surfaces

The rule, everywhere:

> **An authenticated human, on a channel able to carry their decision, confirms a
> Relay-authored Plan.**

Relay authors the approval content (operation, arguments, resolved fan-out, per-Node verdicts,
requester, on-behalf-of claim), so the AI-agent cannot truncate or spin what the approver
sees. An in-band answer is only as trustworthy as the harness holding the session's
credential; an out-of-band decision rides a credential the AI-agent session does not hold.
The difference is "the approval is an assumption about the client" versus "the approval is
evidence."

The rest of this note's design is now decided, and the ADRs are the record:

- **Read auditing**: reads are audited and read output is not retained (ADR-0025).

## Worked example

Gleipnir (machine Account `gleipnir-prod`) dispatches a mutate batch with
`on_behalf_of: ops-team, change: TICKET-123`. A gate rule (mutate + blast > N) parks the Jobs
with `count: 1, requester_allowed: false, channel: out-of-band`. Gleipnir's audience router
reaches Mike, who authenticates out of band, reviews the Relay-authored Plan and approves.
One audit query answers both questions:
`requested_by: gleipnir-prod ✓ · on_behalf_of: ops-team ⚠ · approved_by: mike ✓
(out-of-band, plan-hash …)`.
